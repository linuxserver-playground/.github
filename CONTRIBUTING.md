# Contributing to the LinuxServer.io v2 playground

This file applies to every repository in the `linuxserver-playground` organisation that does not
carry its own. It is written for the `docker-<name>` image repositories; the infrastructure repositories
(`builder`, `workflows`, `ci`, `hub`, `control`) each have an `AGENTS.md` with the same headings that
says what is specific to them.

New here? Start with the [Contribute page](https://linuxserver-playground.github.io/site/contribute/) and the
[harness](https://github.com/linuxserver-playground/harness), which lets an AI coding agent follow this file for
you. You still answer for every line you submit.

Everything here is a proof of concept. Images published from this organisation are not for production
use. The full contract the repositories are built against is
[`CONVENTIONS.md`](https://github.com/linuxserver-playground/builder/blob/main/CONVENTIONS.md) in the
`builder` repository; when this file and that one disagree, `CONVENTIONS.md` wins.

## Gotchas

* Make all your changes before opening a pull request. Every push to an open PR starts a full build and
  test run on GitHub Actions.
* Read, and fill in, the pull request template. Honestly.
  * If this is a fix for a typo (in code, documentation, or the README) please file an issue and let us
    sort it out. We do not need a PR.
  * If the PR is addressing an existing issue include `closes #<issue number>` in the body of the PR.
* If you want to discuss a change first, bring it up in
  [Discussions](https://github.com/orgs/linuxserver-playground/discussions) or on
  [Discord](https://linuxserver.io/discord).

## Decide where the change belongs before writing any code

Our images are built for broad consumption. Every package, env var and init step we add is something we
have to maintain, rebuild weekly and support forever, for every user, whether they use it or not. Work
down this list and stop at the first match:

1. **It is a bug or feature in the application itself** (not in our packaging): it belongs upstream with
   the app's developers. Do not patch, fork or work around upstream application behaviour in the image.
2. **It is an unsupported or reasonable-endeavours environment** (Podman, k8s, Portainer, Watchtower,
   NFS/SMB `/config`, LXC, custom entrypoints; see the
   [support policy](https://docs.linuxserver.io/misc/support-policy/)): we will not add logic to the
   image to accommodate it.
3. **It only matters to one user or one setup**: use a private
   [custom script](https://docs.linuxserver.io/general/container-customization/#custom-scripts) in
   `/custom-cont-init.d` or a
   [custom service](https://docs.linuxserver.io/general/container-customization/#custom-services) in
   `/custom-services.d`. No PR needed.
4. **It is useful to a subset of users** (an extra package, plugin dependency, alternative UI, hardware
   driver, third party integration, extra daemon, niche toggle): it is a
   [Docker Mod](https://github.com/linuxserver-playground/docker-mods), not a change to the image repo.
   Check whether one already exists first.
5. **The large majority of this image's users benefit, or the image is actually broken**: a PR to the
   image repo is appropriate. Examples: the app fails to start, a new upstream release needs a new runtime
   dependency, a permissions bug, a wrong default, incorrect docs in `image.yml`.

"It is only a few lines" is not a reason to put it in the image. If in doubt, open an issue or ask first.

## Image repository layout

```
Dockerfile              amd64, FROM ghcr.io/linuxserver/baseimage-<base>:<tag>
Dockerfile.aarch64      arm64, identical except the base tag
root/                   copied to / in the image; s6-overlay v3 units under root/etc/s6-overlay/s6-rc.d
image.yml               the manifest (schemas/image.schema.json). The only hand-edited metadata file.
package_versions.txt    written by the build, committed on the live branch, never hand-edited
README.md               generated by `builder render`, never hand-edited
AGENTS.md               generated by `builder render`, never hand-edited
LICENSE                 GPL-3.0, generated
.github/workflows/build.yml   ~20 lines, generated, calls workflows/image-build.yml@v1
```

There is no Jenkinsfile, no `jenkins-vars.yml`, no `readme-vars.yml` and no per-repo trigger workflows.
Issue templates and this file come from the org `.github` repository.

### What you may edit

| Path | Edit? | Notes |
| --- | --- | --- |
| `Dockerfile`, `Dockerfile.aarch64` | yes | One per architecture. Any change goes in both. Packages one per line, alphabetical. |
| `root/` | yes | Copied to `/`. s6 scripts start with `#!/usr/bin/with-contenv bash` and `# shellcheck shell=bash`. |
| `image.yml` | yes | The manifest. Source of truth for the README, docs page, stores, proxy confs, build and test settings, and the changelog. Schema: [`image.schema.json`](https://github.com/linuxserver-playground/builder/blob/main/schemas/image.schema.json). |
| `package_versions.txt` | no | Written by the build on the live branch. |
| `README.md`, `AGENTS.md`, `LICENSE` | no | Generated from `image.yml` by `builder render`. |
| `.github/workflows/build.yml` | no | Generated; calls the shared workflow in `linuxserver-playground/workflows`. |

Do not add new top-level files or tooling: no compose files, Makefiles, test suites, linter configs,
pre-commit hooks, extra workflows or `CHANGELOG.md`. A pull request that changes a generated file fails
`builder check`.

Some repos have more than one live branch (`develop`, `nightly`, ...), each with its own `image.yml`.
Target the branch the change applies to and never merge one into another.

## README and documentation

Do not edit `README.md`; it is regenerated from `image.yml` on every change to the manifest. Put
user-facing text in `image.yml` (`summary`, `docs.setup`, `docs.optional_parameters`, the descriptions on
`runtime.*` entries) and run `builder render` to regenerate the files you would otherwise have edited.
The docs page is rendered by the hub from the same manifest.

## Validate with `builder check` and `builder render`

The `builder` tool lives in [`linuxserver-playground/builder`](https://github.com/linuxserver-playground/builder)
and ships as a container. Run it from the root of the image repository:

```bash
# validate image.yml, report generated files that drifted, lint s6 scripts and the changelog
docker run --rm -v "$PWD":/repo ghcr.io/linuxserver-playground/builder:latest check

# rewrite README.md, AGENTS.md, LICENSE and .github/workflows/build.yml from image.yml
docker run --rm -v "$PWD":/repo --user "$(id -u):$(id -g)" ghcr.io/linuxserver-playground/builder:latest render
```

`builder check` exits 1 and prints the file, the field (a JSON path into `image.yml`) and the line on
failure. The PR build runs the same check, so run it before you open the PR. Install it from source with
`pip install -e .` in the builder repo if you prefer a bare `builder check` / `builder render`.

## Update the changelog

If you modify a Dockerfile or anything under `root/`, add an entry at the **top** of `changelog:` in
`image.yml`, one short factual sentence:

```yaml
changelog:
- date: '2026-10-24'
  text: Add libfoo to fix thumbnail generation.
```

`builder check` requires the list to be newest first. Documentation-only changes to `image.yml` do not
need an entry.

## Test it for real

A change that has not been built and run is not ready.

```bash
git clone https://github.com/linuxserver-playground/docker-<name>.git
cd docker-<name>
docker build --no-cache --pull -t <name>:test .
docker run --rm -e PUID=1000 -e PGID=1000 -e TZ=Etc/UTC -v "$PWD/testconfig:/config" -p <port>:<port> <name>:test
```

Confirm `[ls.io-init] done.` appears in the log, the app comes up, and it survives a restart against an
**existing** `/config`, not just a fresh one. The arm64 image can be built on x86-64 (and vice versa)
after registering qemu with `docker run --rm --privileged lscr.io/linuxserver/qemu-static --reset`, then
`docker build -f Dockerfile.aarch64 --platform linux/arm64 ...`.

Once the PR is open, GitHub Actions builds and tests both architectures and publishes the result to
`ghcr.io/linuxserver-playground/untrusted-pr/<name>:pr-<number>-<sha7>` for reviewers (pull requests
from forks upload the image as a workflow artifact instead). The build record and test report for every
run are on the [control plane dashboard](https://ci.thelamer.duckdns.org:8443). PR images are deleted
when the PR closes and are never for production use.

## Pull request rules

* **Disclose AI use.** AI-assisted contributions are welcome and must be disclosed in the PR description:
  which tool, and what it was used for. Undisclosed AI-generated PRs will be closed.
* **A human is accountable.** The person opening the PR must have read and understood every line, built
  and run the image, and be able to answer review questions in their own words. Fully autonomous agents
  must not open PRs or issues.
* **One focused change per PR.** The smallest diff that fixes the problem. No drive-by refactors,
  reformatting, comment rewording or dependency shuffling.
* **No typo or wording-only PRs.** Open an issue instead.
* **Finish before you open.** No drafts iterated in public with a stream of fixup commits.
* **Fill in the PR template honestly** and keep its structure: description, benefit to the wider
  userbase, how it was tested (real commands, real output) and links. Short and plain, no generated
  summaries or bullet lists restating the diff.
* **Commit subjects are short imperative sentences** (`Add krb5-libs for postgresql support`). No
  conventional-commit prefixes, no emoji, no trailers of any kind.
* A PR that touched generated files, or whose manifest does not validate, fails `builder check` with the
  file, field and line.
* A PR is a proposal; it may be declined even if it works. The most common reason is the "where does the
  change belong" list above.
